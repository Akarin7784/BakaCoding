# BakaCoding 笨蛋编程助手产品设计文档

版本 1.3 · 2026 年 10 月 17 日 · 让个人开发者完成超大规模软件的开发与维护

BakaCoding（笨蛋编程助手）是采用 MIT 协议的开源项目，帮助个人开发者完成超大规模软件的开发与维护。系统把整体架构、子系统依赖、功能实现、集成验证和长期工程知识组织成可持续推进的工程闭环。个人开发者负责目标、关键设计和最终验收，工作台承接跨模块协调、任务执行与验证，让项目规模能够超出一个人靠记忆和手工调度所能管理的范围。

核心产品判断是：保留原图的知识优先和按功能滚动交付，将主 BOT 改为有边界的规划器，将固定串行流水线改为受依赖和资源约束的任务图，将相邻 BOT 互审补充为独立验证，将自动知识沉淀改为可审核、可追溯、可失效的资产管理。首版用较少的运行角色完成可靠闭环，默认同时运行一个编码任务。

技术调研核验日期为北京时间 2026 年 10 月 17 日。近期技术证据窗口为 2026 年 9 月 17 日至 10 月 17 日。文中带有来源编号的外部能力属于已核验资料；功能、规模目标、数值目标与技术选型属于本产品的设计建议或待验证假设，均不代表已实现能力或实测结果。

## 1 原架构分析与改造结论

### 1.1 图中的实际工作方式

原图包含需求输入、主 BOT 控制平面、知识与组件库、项目记忆与状态库、功能开发流水线、验证与质量控制、产物与版本管理，以及持续反馈。图中层级编号存在重复，本文按实际职责分析，不将图片中的编号当作实施优先级。

主 BOT 负责理解需求、选择方案、拆分功能、制定规范和调度。功能 BOT 设计本功能并形成编码任务包，快速模型执行代码与测试生成；下一轮功能 BOT 评审上一轮实现，同时设计下一功能。测试、审查和 Git 集成形成门禁，执行结果再写回项目记忆、组件和知识库。

这一构想本质上是围绕功能交付的工程系统。模型只是执行和分析能力，真正决定产品价值的是任务边界、共享事实、验证证据和可恢复的交付过程。

### 1.2 应保留的设计

以功能作为交付单位，能让用户理解“完成了什么”，也便于将需求和测试逐项关联。知识和成熟组件优先，可以减少重复实现。规划与编码分开，有利于按复杂度选择模型。滚动评审有助于提前发现接口不一致。项目记忆独立于模型会话，能支撑跨天工作与供应商切换。

这些收益都有条件：功能需要足够小且可验收，组件要能证明兼容，项目记忆必须由可靠事实更新。仅增加 BOT 数量并不能保证效果。

### 1.3 原图的产品化缺口

| 原图设计 | 具体失败方式 | 产品设计修正 |
| --- | --- | --- |
| 主 BOT 统一全局决策 | 模型误判可扩散到全部任务，长会话丢失约束 | 规划器只提出带版本的计划，状态机、预算、权限由程序执行 |
| A 到 B 到 C 固定队列 | 无依赖功能也等待，复杂依赖被线性顺序掩盖 | 功能构成有向无环图，按依赖、冲突和资源调度 |
| B 评审 A 并设计 B | B 的进度掩盖 A 的问题，双方共享同一错误假设 | 相邻评审保留为衔接检查，独立验证负责门禁 |
| 编码模型生成测试 | 实现与测试可能共同误解需求 | 先冻结验收标准，验证器独立生成边界与反例 |
| 快速模型池固定承担编码 | 复杂改动重复失败，便宜调用变成昂贵返工 | 按任务风险、历史结果和预算路由，失败后受控升级 |
| 统一检索知识和组件 | 过期建议或不兼容组件被当作当前事实 | 按仓库版本、许可、依赖、来源和有效性过滤 |
| 项目记忆混合多类记录 | 模型总结覆盖事实，已修复问题继续传播 | 事实状态、决策、原始证据、候选经验分别保存 |
| 测试通过后自动进入稳定基线 | 旧提交测试结果被用于新提交，合并后产生回归 | 检查绑定提交与树哈希，合并候选重跑必要验证 |
| 自动归档全部经验 | 偶然成功被推广，私有代码进入共享库 | 候选提取后审核，默认仅在本项目可见 |
| 交付到构建产物即结束 | 用户无法判断功能是否可用，也缺少撤销方案 | 提供预览、逐项验收、发布说明、回滚入口 |

### 1.4 建议的新架构

用户输入 → 需求澄清 → 知识检索 → 功能契约 → 用户确认范围和预算 → 任务图调度 → 隔离编码 → 独立验证 → 预览验收 → 合并或导出 → 候选知识沉淀。

跨阶段由四个确定性机制约束：持久化状态机、动作权限、费用台账、证据版本校验。所有角色读取同一项目事实版本，禁止通过聊天历史推断任务是否已完成。

流水线只允许受控重叠：A 编码时可以进行 B 的只读设计；A 未验证前，依赖 A 未冻结接口的 B 不进入实现。两个功能无接口、文件和数据迁移冲突，且预算与运行资源允许时，才开启双任务编码。

### 1.5 首版成功标准

成功标准是个人开发者能持续掌握并推进一个包含大量模块、复杂依赖和长期演进需求的软件系统。系统应把整体目标拆成有边界的阶段成果，在局部执行时遵守全局架构，在多个模块集成后给出系统级证据，并在跨天、跨月执行中保留真实进度和未完成事项。

小功能是可验收的执行单元，整体项目与子系统才是管理对象。完成一个小功能用于验证最小闭环，不能被当作完成超大软件目标的充分证明。

### 2.3 模型与运行框架的选择

产品默认模型已经确定为 DeepSeek V4.1 Flash，官方 API 标识为 `deepseek-flash` [B07][B09]。主 BOT 使用最高档 `max`，Flash 编码流水线使用 `low`，次 BOT 使用中档，对应原生 `high`。产品保留 `medium` 作为中档逻辑值，由适配器显式映射到 `high` [B08]。同源模型是默认方案，不强制要求使用不同供应商。

本轮技术调研中的 GPT、Claude、Gemini 和 Qwen 资料用于能力参考及自定义适配，不改变用户指定的默认模型。应用内模型上线、编码运行框架发布和第三方 API 可用性分别核验，不混为一个能力。

模型 API 与执行运行框架分开配置。默认接入路径需要支持 DeepSeek API，并由 BakaCoding 控制文件、命令、状态、预算和工具循环。Codex SDK、Claude 程序化运行或其他兼容框架可以作为执行适配候选 [B01][B02]，采用前验证它们对用户自定义端点、模型与档位的实际传递能力；不能让某个框架的固定模型菜单限制产品配置。

首版采用显式状态机加执行适配器。供应商配置、角色模型与思考档位作为独立配置契约固定到每次运行，工具权限和质量门禁保持由程序执行。第 14 节定义完整默认值、覆盖规则与兼容校验。

### 2.4 明确不追逐的技术

Scion 是供应商内部工程案例，不应推断为可采购或直接接入的开源组件，也没有理由让个人开发者替换 Git [S04]。模型官方演示、单项排行榜和供应商成本案例不能直接转化为产品承诺。首版也不以多智能体自由对话、超长上下文、自动学习或全量向量化作为卖点。

Git worktree、SQLite、检索、持久化执行和协议连接属于工程基础，其价值不因发布时间较早而失效。本文将其放在基础选型中，未将几个月前的发布冒充近期进展。MCP 接入只在明确需要外部工具时加入；协议版本需协商和固定，本轮不主张存在尚未核实的 10 月新版本。

## 3 产品定位与用户需求

### 3.1 产品定义

BakaCoding 是面向个人开发者的超大规模软件开发与维护工作台。核心价值是把个人的设计决策与多个受控执行角色结合起来，持续管理架构、代码、依赖、验证和交付，使一个人能够有序推进通常需要多人协调的复杂工程。

“超大规模”既包括代码和模块数量，也包括依赖复杂度、系统边界、迭代周期和变更影响范围。产品不以单次生成更多代码定义成功，也不预设必须将所有代码或执行任务放在一台机器上。

### 3.2 目标用户与待完成工作

核心用户是希望独立设计、实现并长期维护大型软件系统的个人开发者。用户可以是大型开源项目维护者、独立构建复杂应用的开发者，或需要在多个子系统间持续推进工作的工程师。是否有团队协作者不是产品成立的前提。

| 场景 | 待完成工作 | 关键结果 |
| --- | --- | --- |
| 从零构建大型系统 | 建立领域边界、接口、依赖与阶段目标 | 从总体设计逐步形成可集成的软件 |
| 持续开发大型代码库 | 快速定位实现位置并理解关联行为 | 局部修改不破坏其他子系统 |
| 跨模块重构或迁移 | 分批修改调用方、实现与数据契约 | 新旧兼容、阶段可运行、结果可追踪 |
| 长期独立维护 | 管理缺陷、依赖升级、架构演进和技术债 | 中断后可继续，历史决策不丢失 |

产品应减少个人掌握全局所需的重复阅读和手工协调，同时把必须由用户决定的问题收敛为可审查的设计选项。

### 3.3 核心痛点与对应能力

超大软件的瓶颈是全局理解、架构约束、依赖管理和系统集成逐渐超出个人可持续处理的范围。一个模型会话无法容纳全部工程知识，多个编码角色又容易各自做出不一致的局部决策。

对应能力为分层项目地图、版本化架构决策、接口契约、依赖驱动任务图、按需上下文、变更影响分析、受控并行、跨模块验证和持续维护队列。费用与预览仍是必要能力，服务于整个项目的持续推进。

### 3.4 定位与竞争边界

Cursor 的近期交付观察、审查和生态扩展说明，产品竞争已覆盖从编码到交付的更长链条 [S09][S10]。Google 将 Antigravity 接入 Gemini macOS 应用，进一步降低了用户从对话发起后台编码的门槛 [S11]。KFPA 不应把“也支持多个代理”当成壁垒。建议聚焦可验证的整体工程能力：个人能掌握项目全局；多个模块遵守共同架构和接口；局部任务能集成为可运行系统；项目状态与知识可跨会话、跨版本持续使用。

用户已有 IDE 和编码工具时，工作台应承接它们之上的项目组织工作。评价重点是大型工程中减少了多少重复理解、依赖遗漏和集成返工，以及用户是否仍能清楚掌握架构和变更。

## 4 首版范围与产品原则

### 4.1 首版交付边界

产品围绕超大项目设计数据模型与执行机制，通过可运行的垂直切片逐步验证，不把小型单仓库定义为长期产品边界。

| 能力域 | 核心设计要求 | 可逐步增强的执行能力 |
| --- | --- | --- |
| 项目组织 | 项目、子系统、模块、仓库、接口与里程碑分层建模 | 多语言解析与更多仓库平台 |
| 需求拆分 | 整体目标拆为依赖明确、可集成的功能任务图 | 大范围变更的拆分质量与自动影响分析 |
| 架构一致性 | 统一约束、版本化决策、接口契约与边界检查 | 自动发现架构漂移 |
| 知识与上下文 | 分层索引、增量更新、按需检索、来源追踪 | 多模态资料和更丰富的语义索引 |
| 执行 | 默认本机 Git worktree，用户可选本地 Docker 或远程 SSH Linux | 多 worker 与依赖允许的并行 |
| 验证 | 局部检查、跨模块契约测试、系统级关键路径验收 | 更多运行环境、性能与兼容矩阵 |
| 交付 | 里程碑集成基线、兼容变更和可恢复的版本集合 | 多仓库发布编排 |
| 人工控制 | 用户审查关键设计、控制权限、接管与恢复 | 更多编辑器入口和任务呈现方式 |

首个可运行切片可先选择一种语言和一种编码适配器，用来验证闭环。正式支持范围需给出运行环境与命令兼容清单；多模块、多仓库和远程 worker 从数据与协议层预留明确边界，不能依靠后期将本地目录字段临时拼接实现。

### 4.2 产品原则

第一，用户围绕功能作决定，系统负责拆分和执行。第二，明确需求和现有行为优先于模型推测。第三，所有重要状态、授权和费用均由程序约束。第四，尽量自动推进可逆步骤，只有范围、费用或外部影响超出授权时才打断。第五，交付需要证据，模型的“已完成”只是一条候选声明。第六，本地优先意味着控制面和文件可在本地，不意味着调用云模型时源码永不离开设备。

### 4.3 自主执行级别

L0 为只读分析，输出建议。L1 为隔离实现，允许在约定工作区内编码、构建、测试和生成预览，首版默认采用。L2 为受控集成，用户启用后可为低风险任务自动创建本地提交或 PR，仍需满足质量门禁和分支保护。生产部署、破坏性数据迁移和外部付费操作按单次明确授权处理，首版不提供全自治发布模式。

## 5 用户旅程与典型场景

### 5.1 首次使用

用户安装后先选择仓库，默认使用本机 Git worktree 直接执行；用户也可选择本地 Docker 或远程 SSH Linux。系统按所选后端检查 Git、可用磁盘、运行环境、依赖、启动与验证命令，并展示当前工作区是否存在未提交修改。不使用 Docker 或 SSH 时不要求配置它们。用户选择正式支持的运行框架，完成凭据配置或跳转到官方授权流程，执行一次小额连通测试。界面明确显示可能传给模型的代码与上下文类型。

系统运行项目原有验证，形成基线：哪些命令通过、哪些失败、哪些未配置。失败必须标注为既有问题。用户确认项目说明、命令和预算后，才开启首个功能。没有测试的仓库可继续做受限实现，但界面持续显示验证缺口，不给出“全部通过”。

### 5.2 需求到交付

用户输入“给文章列表加标题搜索”，系统识别现有列表入口、数据来源和相关组件，并提出最多三个会改变实现或验收的问题。若存在合理默认值，显示可编辑的假设，让用户一次确认。随后生成目标、范围、不做事项、验收项、改动位置、风险和预算上限。

确认后，功能卡进入队列。用户看到当前阶段和下一步，无需阅读所有工具日志。系统完成实现与验证后给出预览地址、修改摘要、逐项验收和残余风险。用户可以接受、提出局部修改、在 IDE 接管或放弃变更。接受后系统按设置合并到项目分支或导出 PR 草稿；生产发布保持独立动作。

### 5.3 中途修改需求

用户在执行中追加“搜索还要支持标签”。系统先比较原契约，提示这会新增范围，给出增量费用和受影响验收项。当前已安全完成的步骤保留，依赖旧契约的设计和验证标记失效。用户确认新版本后继续；用户未确认时，原授权范围内不受影响的任务可以继续。

### 5.4 失败恢复

网络中断后界面显示供应商断连与最后一个完成步骤；系统按退避策略尝试恢复，超过上限转入等待。应用重启先重新识别子进程、工作区和持久化记录，不直接重新执行未知结果的外部操作。费用账单尚未确认时，将对应金额视为预留。用户选择继续后从可验证的检查点运行。

### 5.5 多模块与多仓库开发

个人开发者可以将多个仓库映射到一个项目，定义所属子系统、依赖接口和版本关系。系统生成仓库间的变更集合和集成顺序，逐仓库保存基线与产物。一个仓库验证通过不能直接代表整个项目已通过。

不同设备可以作为同一用户的执行节点，由单一权威协调器领取任务并回传证据。禁止通过同步一个 SQLite 文件实现分布式状态共享。外部贡献者仍可以通过 Git 和 PR 协作，产品不要求用户先建立团队组织。

## 6 信息架构与页面设计

### 6.1 一级导航

导航包含项目、架构、任务、知识、设置。进入项目后提供总体目标、子系统地图、接口与依赖、里程碑、功能看板、运行详情和分层验收台。账单属于设置和运行详情的共同入口；故障只在需要处理时显示，不做满屏监控中心。

### 6.2 项目概览

首屏显示整体目标、当前里程碑、子系统进度、依赖阻塞、各仓库集成基线、架构风险、待处理设计决定和资源消耗。主按钮为“添加功能”。没有项目时直接给出“打开本地仓库”，不要求注册和购买后才能看到产品价值。云协作和托管能力另行登录。

### 6.3 功能卡与需求确认页

功能卡显示标题、状态、负责人、验收完成数、当前消耗及阻塞原因。确认页分为需求正文、系统理解、验收清单、计划与预算四段。用户可直接编辑每项验收，保留修改历史。风险较高时显示具体动作，例如“需要修改用户表结构”，而不是只给一个抽象高风险标签。

主按钮文案示例：“按此范围开始，上限 ¥30”。该金额属于示例预算，不代表实际估价。点击前显示包含哪些动作、哪些动作仍需确认，以及超预算后的处理方式。

### 6.4 功能看板

看板按待确认、待执行、进行中、待验收、已交付组织。暂停、失败、超预算为卡片状态，避免通过增加大量列破坏理解。切换到依赖视图时显示前置功能和阻塞链。拖动优先级不能越过真实依赖，系统解释被阻止的原因。

### 6.5 运行详情

顶部显示目标、预算、已花费、运行环境和暂停按钮。中部是“已完成、正在做、下一步”的阶段时间线；底部按需展开工具调用、测试日志、模型选择和知识引用。运行状态不能用无依据的百分比，长步骤显示经过时间和可核验里程碑。

“暂停”先阻止新动作，再等待当前可中断步骤结束；强制停止需要说明可能保留半成品。“在 IDE 接管”暂停代理写入、导出交接摘要并开放工作区。用户手工修改后，系统重新扫描差异，不能直接用旧检查结果继续合并。

### 6.6 验收台

左侧为验收项，中间为 Web 预览或命令产物，右侧为代码摘要和验证证据。每项验收有通过、失败、未验证、需人工判断四种结果。无界面任务用 API 示例、测试报告或文件差异替代预览。预览失败时仍展示日志和可审查补丁，但禁止将功能标为可运行交付。

底部按钮为“接受并集成”“提出修改”“保留分支稍后处理”。未解决的阻塞项直接关联对应修改入口。不能把低置信度模型自评默认显示为绿色通过。

### 6.7 关键界面草图

```text
项目  ArticleTool       基线 a81f…       今日 ¥12.6 / ¥50
功能  标题搜索          进行中           [暂停] [在 IDE 接管]
```

### 6.8 打断策略

一次需求只集中询问真正影响决策的问题。测试重试、受控文件编辑和范围内命令不反复请求确认。范围变化、无法判定的数据操作、额外费用、未知权限或生产影响需要用户处理。用户离开时任务可以停在明确状态，不能通过默认超时替用户批准。

## 7 功能需求与验收标准

P0 为首版发布必需，P1 为闭环稳定后的扩展。以下验收采用可观测结果，而非模型主观判断。

| 编号 | 优先级 | 功能要求 | 验收条件 |
| --- | --- | --- | --- |
| FR01 | P0 | 仓库接入与基线检查 | 未提交文件可见；检查前后用户目录内容不被覆盖；已有失败独立记录 |
| FR02 | P0 | 需求转功能契约 | 目标、范围、验收、预算、基线、版本均必填；缺失时不能进入实现 |
| FR03 | P0 | 输入来源隔离 | 附件、网页、日志中的命令不提升为用户授权；恶意样本不能扩大工具权限 |
| FR04 | P0 | 可编辑计划与依赖 | 用户可调整顺序；循环依赖被阻止并显示路径；依赖未满足不能调度 |
| FR05 | P0 | 上下文和知识引用 | 每个采用的决策能追溯来源版本；失效条目不得自动进入执行上下文 |
| FR06 | P0 | 默认 worktree 与可选执行后端 | 默认本机 worktree；用户可选本地 Docker 或 SSH Linux；原目录修改保留，后端检查失败不静默切换 |
| FR07 | P0 | 编码运行适配 | 事件可流式展示；错误分类明确；不依靠解析自然语言判断成功 |
| FR08 | P0 | 预算与运行限制 | 单任务、日额度均检查预留；达到额度后不发起新计费调用 |
| FR09 | P0 | 暂停、取消和恢复 | 暂停后不再启动新步骤；重启恢复已完成检查点；不重复创建提交或 PR |
| FR10 | P0 | 独立验证 | 验证器不能修改实现或冻结的验收；结果绑定确切代码版本 |
| FR11 | P0 | 修复闭环 | 每次失败生成带证据的修复任务；达到重试上限后等待用户，不无限循环 |
| FR12 | P0 | 功能预览 | 端口冲突有明确提示；预览绑定任务和版本；退出后可回收进程 |
| FR13 | P0 | 人工接管 | 代理停止写入后才交接；人工修改使受影响验证失效；可再交还代理 |
| FR14 | P0 | 验收与集成 | 验收未通过不能自动集成；基线变化后必要检查重跑；集成操作可追溯 |
| FR15 | P0 | 交付报告导出 | 包含需求版本、提交、验收证据、未解决问题、费用和撤销说明 |
| FR16 | P0 | 项目记忆候选审核 | 候选与已批准记录明确区分；删除或失效后不会继续自动引用 |
| FR17 | P0 | 凭据与数据控制 | 凭据不写入日志、报告或项目提交；可查看并删除本地任务记录 |
| FR18 | P0 | 角色模型自定义配置 | 主 BOT max、编码 low、次 BOT 中档默认正确；用户可逐角色覆盖端点、模型与档位；不支持的参数明确报错 |
| FR19 | P0 | 受控并行与执行节点 | 依赖、冲突、资源与租约共同约束调度；无并发越权覆盖；集成收益可验证 |
| FR20 | P0 | 项目分层与全局进度 | 子系统、模块和里程碑可追踪；功能完成不会直接提升系统整体为已完成 |
| FR21 | P0 | 多模块接口与变更集合 | 跨模块变更声明契约版本与兼容范围；集成结果绑定全部相关基线 |
| FR22 | P0 | 长期任务与里程碑验收 | 跨会话恢复目标、约束和未完成事项；系统级关键路径通过后才能接受里程碑 |

### 7.1 需求契约的完成定义

至少包含一句用户价值、明确的功能边界、可逐条验证的验收、现有行为约束、允许修改范围和风险。系统可以建议拆分，但不能为了显得进度快而把需求切成大量没有用户价值的小任务。一个功能通常应能形成一次连贯演示，大小通过试用校准。

### 7.2 异常体验

错误分为需求不足、环境不可用、供应商限制、测试失败、权限阻止、预算不足和集成冲突。每类错误提供“发生了什么、保留了什么、可以怎么继续”。用户可以导出已完成补丁，失败任务不能让成果被锁在不可访问的会话中。

## 8 智能体职责与协作协议

### 8.1 全局规划与局部执行角色

| 角色 | 输入与输出 | 允许动作 | 不承担的权力 |
| --- | --- | --- | --- |
| 全局规划器 | 总体目标、工程地图 → 架构约束、里程碑和跨模块任务图 | 提出全局拆分与关键决定 | 不将局部完成当作系统完成 |
| 子系统协调角色 | 子系统目标、契约和依赖 → 模块任务与集成候选 | 管理局部依赖、提交变更请求与证据 | 不擅自修改全局架构或跨模块契约 |
| 功能设计器 | 已确认契约 → 实现方案和任务包 | 读代码与规范，提出接口、测试计划 | 不自行扩展范围，不认定交付成功 |
| 编码执行器 | 任务包 → 补丁、实现说明、开发测试 | 在指定工作区使用允许工具 | 不改冻结验收，不自行豁免门禁 |
| 独立验证器 | 契约、候选提交 → 验收和风险证据 | 在验证环境运行检查，读实现 | 不修改候选实现，不合并，不授予权限 |
| 运行协调器 | 持久化任务与事件 → 状态和动作 | 确定性调度、配额、暂停和恢复 | 不是模型，不接受文本绕过规则 |

规划与设计角色可复用同一模型配置，但按全局、子系统和任务隔离上下文。子系统角色按实际复杂度创建，不为每个目录常驻一个代理。主 BOT 默认绑定 primary 配置，子系统协调与功能设计绑定 secondary 配置，编码执行器绑定 coding 配置。验证器默认继承 secondary，使用独立上下文和确定性测试，也允许用户单独配置模型。使用同源模型不触发阻断或强制异源切换。

### 8.2 编码任务包

每个任务包包含 task_id、feature_revision、base_commit、允许文件与命令、目标行为、接口约束、知识引用、开发测试、禁止动作、交付格式、费用上限和失效条件。任务包内容通过 schema 校验后才能执行。模型返回的额外字段不能转化成权限。

```json
{
  "task_id": "task_search_01",
  "feature_id": "feature_search",
  "feature_revision": 2,
  "repository_id": "repo_main",
  "base_commit": "<完整提交哈希>",
  "milestone_id": "milestone_01",
  "contract_refs": [{"id": "search_api", "revision": 1}],
  "acceptance_ids": ["AC01", "AC02", "AC03"],
  "write_paths": ["src/features/articles/**", "tests/articles/**"],
  "command_profile": "web_verified_commands_v1",
  "knowledge_refs": [{"id": "list_rules", "revision": 3}],
  "limits": {"max_attempts": 2, "budget_minor": 3000, "currency": "CNY"},
  "forbidden_actions": ["deploy_production", "edit_secrets", "change_acceptance"]
}
```

该结构是产品接口草案；3000 表示人民币分，费用台账还要保留供应商原币种和换算快照。通配路径是授权意图，执行器必须解析真实路径并处理符号链接，不能只做字符串前缀判断。

### 8.3 角色间交接

交接消息至少包含结果摘要、产物哈希、证据地址、未解决事项和下一状态建议。协调器验证产物确实存在且版本匹配后转移状态。长日志写入本地文件，只传摘要与可回读位置。开发者提供的仓库规范优先于模型习惯，但其中涉及敏感动作的指令仍受用户授权和程序权限约束。

### 8.4 滚动互审的保留方式

设计 B 前可以检查 A 的公共接口、组件和已知问题，并把不一致作为 issue 提交。B 不直接在自己的工作区修复 A。若问题阻塞 B，协调器暂停 B 的实现并派生 A 的修复任务；若不阻塞，B 可以继续设计。相邻审查通过只是附加证据，不改变独立门禁结果。

## 9 任务状态与调度机制

### 9.1 状态机

```text
Draft → NeedsConfirmation → Ready → Designing → Implementing
                                            ↓
                         Fixing ← Verifying → AwaitingAcceptance
                            └────→ Verifying          ↓
                                                Integrating → Delivered

执行态可进入 Paused / Blocked / BudgetExceeded / Failed / Cancelled
恢复时回到已核验的检查点，保留原事件，不清空运行历史
```

功能状态与运行状态分开。一次功能可以有多次执行尝试；失败不等于需求被删除。Delivered 表示功能通过约定验收并集成或按约定导出，不表示已经部署生产。用户仅保存候选分支时保持 AwaitingAcceptance 或标记为 ArchivedCandidate。

### 9.2 转移规则

| 转移 | 必需条件 | 条件失败时 |
| --- | --- | --- |
| Ready → Designing | 契约已确认，基线可访问，预算足够 | 说明缺项，保持阻塞 |
| Designing → Implementing | 任务包校验通过，依赖满足，工作区分配完成 | 不启动编码，派生澄清或环境任务 |
| Implementing → Verifying | 候选提交或树快照存在，工具结果完整 | 保留补丁并报告不完整 |
| Verifying → AwaitingAcceptance | 必需检查通过，无未处理阻塞项 | 修复或等待人工判断 |
| AwaitingAcceptance → Integrating | 用户接受或既有自动集成策略满足 | 保留候选，不擅自合并 |
| Integrating → Delivered | 候选合并树验证有效，提交写入成功 | 回到验证或冲突处理 |

### 9.3 调度策略

先处理阻塞当前里程碑的接口和集成问题，再处理依赖关键路径与用户优先级。全局规划器维护里程碑与子系统依赖，模块执行器只处理获授权的局部任务。知识检索、设计和验证可在资源允许时重叠。实现并发默认一，整个应用限制模型并发与测试进程数量。用户启用双任务后，调度器检查文件区域、公共接口、锁文件、迁移和资源冲突；修改依赖清单、全局配置和数据库结构的任务默认独占执行。

同一文件无重叠并不意味着语义无冲突。接口和配置依赖来自设计器建议及静态扫描，存在不确定性时降为串行。系统保留排队理由，用户看到“等待接口冻结”，而不是无法解释的空转。

### 9.4 重试与幂等

供应商短暂错误可执行有限退避重试；验证失败按 issue 修复，不复用网络重试逻辑。默认同一问题允许两轮自动修复，此数字是初始产品设置，可通过评估调整。问题未减少、重复出现同类失败或预算不足时停止自动循环。

步骤使用 run_id、step_id 和幂等键。命令、提交、推送和 PR 创建分别记录请求中、已确认、结果未知。网络超时后先查询真实外部状态。不能声称外部副作用能与本地数据库实现统一的精确一次提交；产品需要查询、去重和补偿。

### 9.5 取消与基线变化

取消停止后续动作，保存检查点和差异，已发生的云调用费用不能撤回。清理工作区前列出未归档文件，避免删除人工成果。基线变化后，设计器生成影响分析；受影响的实现、验收和预算估计需更新。仅修改文档不必重跑全部浏览器测试，但必须有可靠的影响规则，缺少规则时使用保守检查集。

## 10 知识与组件产品设计

### 10.1 四类信息分开管理

项目事实包括仓库版本、真实任务状态和命令结果，只能由可信操作或人工确认更新。设计决策包括选择理由、被否决方案和适用边界，需要责任人和版本。运行经验包括某次错误及修复方式，默认只是候选。复用资产包括技能、模板和组件，需具备完整来源、许可、兼容信息及验证记录。

聊天摘要只用于恢复上下文，不能覆盖以上信息。模型可以提出“项目使用某框架”的候选事实，系统必须通过代码、依赖清单或用户确认建立证据。

### 10.2 知识优先的实际执行

先确定任务对应的基线、语言和运行环境，再检索当前仓库中的规范、相似实现、测试和历史决策；其次检索用户批准的跨项目资产；只有需要新技术信息时才访问外部官方资料。首版以关键词、路径、符号和结构化标签检索为主，可选语义检索，不要求上传整个仓库。

检索结果先按权限、版本、许可和适用环境做硬过滤，再按相关性与验证记录排序。排序得分不是正确性概率。没有可靠结果时明确告知无可复用方案，设计器可以提出新实现，不能为了展示复用率强行引入组件。

### 10.3 知识卡片规格

| 字段 | 规则 |
| --- | --- |
| 身份 | knowledge_id、revision、类型、标题、所有者 |
| 来源 | 文件或网址、提交哈希、原始证据、记录时间 |
| 适用范围 | 项目、技术栈、版本区间、平台、目录或场景 |
| 有效性 | 状态、最近验证时间、失效触发条件、替代条目 |
| 可信程度 | 人工确认、自动测试支持、单次观察；不用无依据百分数 |
| 权限 | 本项目、本人跨项目、指定团队；默认本项目 |
| 复用条件 | 许可、来源证明、依赖限制、保留署名要求 |

状态流转为 Candidate → Approved → Deprecated 或 Rejected。Approved 条目变更内容生成新版本；已开始任务继续使用固定版本，检测到关键安全或兼容失效时暂停相关步骤。用户撤回共享后停止后续引用，并列出已使用的项目，不能承诺远端已导出的内容自动消失。

### 10.4 组件复用决策

优先复用项目现有组件，其次选择来源明确且版本兼容的依赖，最后生成新组件。复用前比较接入成本、维护成本和风险，不能只按代码量计算收益。外部组件要检查许可、依赖、更新状态、必要的安全信息及测试；许可证结论不确定时交给用户判断或换用明确的替代项。

首版不自动把用户代码发布为公共组件。交付完成后提取候选经验，例如“该仓库的测试需要启动临时数据库”，用户点击“保存到项目知识”后才成为常规检索内容。跨项目复用需要单独确认可共享内容，秘密、客户数据和第三方受限代码不得混入。

### 10.5 上下文预算与失效

为指令、任务契约、代码证据、知识和历史分配可调预算，大日志落盘、摘要可回读，技能按需加载。这些做法与近期 Deep Agents 的上下文实践方向一致 [S05][S06]。本产品不直接照搬其默认阈值，需按选定运行框架和任务评估。

固定保留用户最新要求、禁止动作、验收和当前版本。摘要后执行一致性检查，防止预算、授权或待处理问题遗漏。仓库依赖变化、来源删除、命令失效或用户撤回时，相关知识标记为待重验；检索索引和缓存同步失效。

## 11 质量与交付证据

### 11.1 分层质量门禁

G0 为基线诊断，识别既有失败。G1 为确定性检查，包括格式、类型、构建和相关现有测试。G2 为功能验证，按冻结验收检查正常路径、边界、错误和回归。G3 为风险检查，依据变更加入依赖、秘密和静态安全扫描。G4 为用户预览与接受。G5 为合并候选树验证，避免基线推进后旧结果失效。

每个项目拥有版本化检查配置。检查可标为 Required、Advisory 或 NotApplicable。只有明确不适用的检查可以排除，未运行和基础设施错误不等于通过。新仓库没有测试时，先加入最低可验证检查并保留缺口，不能将空测试集合当作高质量证据。

### 11.2 验收证据格式

每项验收记录 acceptance_id、feature_revision、candidate_commit、tree_hash、environment_digest、check_definition_revision、命令或交互步骤、结果、时间、日志或截图哈希、验证主体和已知限制。环境摘要至少包括运行镜像、依赖锁文件和关键配置的无秘密指纹。

浏览器截图只能证明某一状态被呈现；交互与业务行为应由自动化步骤或人工确认支持。模型阅读代码后推测“应该通过”必须标为未验证。确定性检查失败时，不允许通过模型自评分数抵消。

### 11.3 防止实现和测试互相掩盖错误

验收在实现前确认；编码执行器可以新增开发测试，但不能修改冻结要求。验证器使用独立环境，依照契约补充反例，特别检查权限、空值、异常、重复提交和旧行为。若认为验收错误，生成变更建议交用户确认，不能悄悄改掉测试使其通过。

高风险任务设置更高验证标准，例如鉴权需要未登录与越权用例，迁移需要备份恢复演练，支付需要幂等和重复回调测试。首版不能可靠验证的类别应限制为分析或人工辅助，不以“所有测试通过”宣称业务安全。

### 11.4 门禁结论

通过表示所有必需检查有效且无阻塞项；需要修改表示发现可修复缺陷；阻塞表示环境、权限、需求或预算使系统无法继续；需人工判断用于 UX、业务语义或残余风险。非安全类可豁免项允许用户记录接受理由、范围和到期条件；程序权限与秘密保护不能被模型或普通豁免绕过。

### 11.5 交付包

交付包包括功能说明、需求和验收版本、完整提交哈希、变更文件摘要、构建或运行方式、验收矩阵、截图或日志链接、未解决问题、模型与运行框架版本、实际与预留费用、撤销步骤。导出 Markdown 和机器可读 JSON；生成的构建文件可选，不能将未包含的运行依赖隐含为已交付。

在用户控制的项目分支上集成，默认不改写提交历史。存在后续提交时撤销应生成 revert 候选，不能直接 reset 并丢弃其他工作。数据库和外部副作用需要单独恢复方案，Git 撤销不能被描述为完整业务回滚。

## 12 推荐系统架构

### 12.1 本地优先拓扑

```text
本地界面 React 和 TypeScript
  ├─ 项目概览  功能看板  运行详情  验收台  知识管理
  └─ 经鉴权的本机 API 与事件流
       ↓
本机协调服务
  ├─ 工程地图  架构约束  接口契约  里程碑与跨仓库基线
  ├─ 状态机  任务图  预算预留  动作策略  证据校验
  ├─ SQLite 事实与事件  本地内容寻址产物  操作系统凭据库
  ├─ 知识检索  仓库索引  版本与有效性管理
  └─ 编码运行框架适配器
       ↓
用户选择执行后端
  ├─ 默认本机执行  可选本地 Docker  可选远程 SSH Linux
  ├─ 每任务 Git worktree 与工作分支
  ├─ 按后端实施路径权限、凭据、进程管理与资源限制
  ├─ 编码进程  独立验证环境  任务预览进程
  └─ 受控调用 → 模型 API 或正式支持的供应商运行框架

可选执行节点  本机或远程 worker  按租约领取任务并回传证据
可选外部连接  Git 远端  PR 平台  文档源
```

首版由桌面壳启动本机服务和界面，业务逻辑不依赖桌面壳。建议先用 Electron 以降低 TypeScript 团队集成进程、凭据和跨平台能力的成本；Tauri 可在包体与资源消耗成为实测问题后评估替换。两者均为工程选择，不是近期新技术结论。界面可以用轻量 Web 构建，不需要为了本地单用户功能引入完整 SaaS 服务架构。

### 12.2 存储与执行选型

| 模块 | 首版建议 | 选择理由与约束 |
| --- | --- | --- |
| 界面 | React、TypeScript、组件库 | 与现有 Web 开发流程一致，便于构建验收界面 |
| 本机服务 | Node.js、TypeScript、显式 schema | 共享接口类型，控制进程与事件；版本在实施时固定 |
| 事实状态 | SQLite 加 WAL，本地单协调写入 | 适合单机轻量任务；写事务必须短，避免阻塞 [B04] |
| 事件与产物 | 追加事件、本地文件、内容哈希 | 支持重放、去重、日志回读和报告导出 |
| 任务执行 | 持久化状态机、租约、步骤日志 | 单机无需独立部署分布式工作流集群 |
| 工作区与执行 | 默认本机 Git worktree；本地 Docker 或远程 SSH Linux 由用户选择 | 分支与目录管理使用 worktree，权限和进程边界按后端能力分别说明 [B03] |
| 索引 | 文件清单、符号、全文搜索 | 先证明命中与维护成本，再加入向量检索 |
| 模型与编码 | DeepSeek V4.1 Flash API 加受控执行适配器 | 逐角色传递 max、high 与 low；执行框架不得覆盖用户模型设置 [B07][B08] |
| Web 验证 | 项目测试工具及浏览器自动化 | 以实际行为和可复查证据验收 |
| 可观测 | 本地结构化事件和费用明细 | 默认不上报源码；可选脱敏诊断 |

LangGraph 的持久化能力和 Temporal 的工作流执行可供后续方案比较 [B05][B06]，由实际执行拓扑决定是否采用。单机可从轻量状态机起步，多机执行与长周期恢复则需要统一持久化协调。避免同时让 KFPA、运行框架和另一个编排系统各自重试同一动作。

### 12.3 工作区与安全边界

默认使用 Git worktree 管理任务分支和工作目录，并在本机直接运行编码、构建与测试。Docker 与远程服务器都不是默认依赖。用户可在项目设置中选择本地 Docker 或远程 SSH Linux；界面明确显示当前执行位置、工具链和资源来源。

| 后端 | 工作区位置与执行方式 | 必需检查 | 边界 |
| --- | --- | --- | --- |
| local 默认 | 本机仓库派生 worktree，本机工具链直接执行 | Git、工具链、磁盘、命令、端口 | worktree 隔离代码目录，不隔离宿主用户权限 |
| docker 可选 | 本地 Docker 中运行任务，协调器管理 worktree、挂载与产物 | Docker 引擎、选定镜像、挂载、网络与资源 | 默认非特权，不挂载 Docker socket；能力由容器配置决定 |
| ssh-linux 可选 | SSH 连接用户 Linux，在远端仓库建立 worktree 并执行 | 主机密钥、登录、Linux、Git、工具链、目录权限与端口转发 | SSH 提供远程通道；执行权限由远端用户和系统策略决定，不默认要求 Docker |

每个任务从确认的基线创建独立 worktree 和分支。原仓库有未提交修改时，默认从已提交基线开始并提示；需要包含当前修改时先建立可审查快照，不能自动 stash 或覆盖原目录。工作区建立、合并与清理由协调器负责，清理前检查人工修改和未归档产物。

Docker 模式挂载本任务所需目录，不扩大到整个宿主文件系统。Git 管理由宿主协调器执行；若项目构建必须在容器内访问 Git，则配置容器内独立仓库与 worktree 或经过验证的元数据路径映射，不能直接复制带宿主绝对路径的 .git 指针。镜像需由用户选择并固定版本，不能在未配置时悄悄回退到本机。

SSH 模式使用用户选择的 SSH 配置项和凭据引用，严格验证主机密钥，支持已有 SSH agent，不将私钥写入项目配置或日志。远端维护自己的仓库和 worktree，通过 Git 或受控快照传递确认基线及变更，不能把本机 worktree 的 .git 指针直接复制到远端。记录远端提交、环境指纹、任务与进程标识；结果回传后校验提交与产物哈希。

依赖安装和项目脚本按用户选定的执行策略运行。验证可在同一后端的新 worktree 或新容器中进行，记录真实环境和隔离能力；本机或 SSH 直接执行不宣称具备容器或虚拟机级隔离。默认环境配置不强制安装 WSL2，用户采用本地 Docker 时遵循其已安装运行环境的要求。

### 12.4 单机恢复设计

协调器是唯一状态写入者，领取步骤时事务写入租约、预算预留和事件意图；工具返回后记录证据和新状态。重启时过期租约进入恢复检查，按真实进程、产物和外部查询判断继续位置。运行框架会话恢复是可选能力，产品恢复不能只依赖供应商的会话 ID。

本地 API 仅监听回环地址，使用每次启动或配对生成的凭据，校验 Origin 与请求权限，避免恶意网页控制本机工具。预览与控制 API 使用不同端口和权限，预览内容不能获得协调器凭据。

### 12.5 多执行节点与远程运行

本地工作台保持个人控制入口，默认使用 local 后端。项目可选 docker 或 ssh-linux，每个任务在启动时绑定后端、工作区、环境配置修订和模型配置快照。模型服务与代码执行位置独立配置，选择远程 SSH 不会改变 DeepSeek 默认角色档位。

执行配置的覆盖顺序为单次运行、项目、用户、内置默认。选择 Docker 时必须指定可用镜像；选择 SSH Linux 时必须指定连接与远端目录。验证失败时报告具体缺项，禁止自动改用其他后端。切换环境只影响新运行或重新派发的未执行步骤，已完成证据按实际环境保留；在不同环境重建候选后重新验证。

单人模式可由本机协调器经 SSH 管理远端执行，不强制用户部署数据库、常驻团队服务或集群。远端步骤需有可查询的任务、进程和日志记录，SSH 断连不能直接等同于任务失败，也不能在未知外部副作用时盲目重试。预览按配置通过 SSH 隧道访问，并管理端口冲突及关闭后的隧道回收。

后续扩展多个 worker 时仍采用单一权威协调器、租约和资源配额。按实际拓扑选择持久化服务，不将多机环境配置作为使用基础功能的前置条件。执行配置示例见仓库 config/execution.example.json；该文件是契约草案，目前没有运行程序读取。

| RoleModelConfig | id、revision、scope、role、model、effort、limits、fallbacks | 逻辑档位与实际参数可追踪，覆盖不影响在途步骤 |
| Step | id、run_id、idempotency_key、lease、state | 幂等键唯一，未知结果必须核查 |
| Workspace | id、task_id、branch、path、base_commit | 一个编码写入者，清理前检查未保存内容 |
| Artifact | id、hash、path、kind、retention | 按内容校验，不以可变路径证明真实性 |
| Evidence | id、acceptance_id、tree_hash、environment、result | 验证结果只对对应候选与环境有效 |
| Issue | id、evidence_id、severity、owner、resolution | 关闭需有修复或豁免证据 |
| Knowledge | id、revision、status、scope、source、validity | 候选不等于批准，失效要传播 |
| UsageLedger | id、run_id、provider_currency、reserved、actual | 已花费加预留共同参与额度检查 |
| ActionGrant | id、scope、actor、expiry、revoked_at | 文本不能扩大授权，过期立即生效 |
| Event | id、sequence、aggregate_id、type、payload | 单项目顺序可回放，不覆盖历史 |

Project、Milestone、Subsystem、Module、Feature、Task、Run 和 Evidence 形成从整体目标到局部证据的追踪链，ChangeSet 关联跨仓库结果。实体删除区分用户可见删除、缓存清除和审计记录保留；保留期限由本地设置控制。日志可能包含源码，不能只把“数据库删除”当作清除所有副本。

### 13.3 适配器能力契约

每个适配器声明支持的模型、事件类型、会话恢复、结构化输出、权限控制、成本回报、取消语义和沙箱方式。最低要求为可观察的动作、明确的完成和失败状态，以及宿主侧可以执行预算和权限限制。缺少某项能力时界面明确禁用相关模式，不能通过解析一句“完成了”补足协议。

## 14 模型路由与预算

### 14.1 默认角色配置

| 角色配置 | 职责 | 默认模型 | 产品思考档位 | DeepSeek 实际档位 |
| --- | --- | --- | --- | --- |
| primary | 主 BOT、全局目标与架构规划 | DeepSeek V4.1 Flash | 最高 max | max |
| secondary | 次 BOT、子系统协调、功能设计和滚动互审 | DeepSeek V4.1 Flash | 中档 medium | high |
| coding | Flash 编码流水线、实现与开发测试 | DeepSeek V4.1 Flash | low | low |
| verifier | 独立上下文验证与证据分析 | 默认继承 secondary，可单独覆盖 | 默认中档 | 默认 high |

官方模型 ID 使用 `deepseek-flash`，展示版本为 DeepSeek V4.1 Flash。DeepSeek 原生支持 `low / high / max`，最高档是 `max`；官方将兼容值 `medium` 映射为 `high` [B07][B08][B09]。本产品把“中档”明确解析为原生三档的中间档 high，记录逻辑值与发送值，不能用 xhigh 代替最高档。

所有默认角色启用思考模式。Chat Completions 协议通过 thinking 和 reasoning_effort 发送参数；其他协议由对应适配器转换，不能将同一字段名直接用于所有接口 [B08]。模型名称由供应商配置和能力探测确定，不能把展示名称直接当作 API ID。

### 14.2 自定义配置与生效规则

用户可分别配置每个角色的服务商、API 地址、协议、模型 ID、思考档位、输出上限、超时、并发、预算和显式回退列表。支持同源或异源组合，也支持自定义兼容端点。新建子系统与功能 BOT 继承 secondary，编码任务继承 coding，用户可以按项目或单次运行覆盖。

设置页提供连接配置、角色绑定和实际参数预览。连接配置集中管理凭据引用与服务商能力，角色绑定展示主 BOT、次 BOT、编码流水线和验证器各自的模型和档位。保存前执行静态校验，连接测试与计费模型试调用分别展示。导入和导出采用版本化 JSON，导出不包含密钥。

配置优先级由高到低为单次运行覆盖、项目配置、用户配置、内置默认。采用字段级合并，但 provider 或 model 变化后重新校验关联的协议、档位映射和能力，不能沿用旧模型参数。继承关系禁止形成循环。缺省参数只能使用可见的继承值或文档化默认值。

每次运行固定配置修订，并记录供应商、端点、API 模型 ID、服务商报告版本、逻辑档位、实际请求参数和来源。自定义端点无法返回确切版本时标记版本未知，不伪造固定版本。配置更新只影响新运行或尚未发起的步骤；在途调用保持原参数，恢复时使用原快照，改配重跑产生新的运行记录。

能力校验包含模型可用性、档位、工具调用、流式事件、输出结构、用量、取消和恢复。官方模型元数据可作为 DeepSeek 能力探测入口，自定义端点不能假定具有同样字段 [B09]。不支持的档位默认报错并给出可选值；只有用户明确设置了映射规则时才转换，并在界面显示原值和实际值。

默认关闭自动模型切换和自动跨服务商回退。失败或复杂任务可以提出升级建议，但执行仍以用户配置为准；同源模型配置不被强制更改。用户启用自动路由时需明确允许的模型、档位、条件和预算边界，任何实际切换都进入运行记录。模型别名对应的供应商版本变化时提示并要求确认，不自动把“最高档”绑定到未来新增档位。

配置文件示例位于仓库 config/models.example.json，是配置契约草案，目前没有运行程序读取。默认示例定义 primary=max、secondary=medium、coding=low，适配器将 medium 映射为 high，verifier 继承 secondary。所有密钥使用 credential_ref 引用，不提交密钥正文。

### 14.3 成本计算

成本包含模型输入与输出、缓存、嵌入或检索调用、其他计费工具、托管算力和存储。自托管本地执行的设备时间单独展示为资源消耗，不伪装成零成本。费用估计显示区间和依据，最终用供应商可确认的账单事件校准。

```text
单步估算 = 未缓存输入量 × 输入单价 + 输出量 × 输出单价
         + 缓存读写费用 + 计费工具 + 执行环境费用

可用额度 = 上限 − 已确认费用 − 未结算调用预留
准入条件 = 本次最大可承诺费用 ≤ 可用额度
```

默认费用来源切换为 DeepSeek 对应模型的官方价目，并区分缓存命中、未命中与峰谷时段 [B07]。自定义模型使用该服务商的价格配置和账单信息。费用计算还要包括规划、编码、验证、失败重试和多轮调用，不能用一次请求代表完整功能成本。配置中没有可靠价格时显示费用未知，不能显示零费用。

### 14.4 预算策略

用户设置任务上限和每日上限，可选按供应商原币种或本地展示币种。显示币种使用记录日期的明确汇率快照，并留出汇率与账单延迟缓冲，不能把人民币上限当成未经兑换就能精确约束的美元账单。

每次调用前预留输出上限和工具费用；有代理内部多轮调用的运行框架，必须有可执行的总限制或由宿主控制每步准入。只提供事后 token 统计的适配器，不能承诺严格硬预算，应标记为估算控制模式并采用更低并发。达到阈值提醒，触及可执行硬上限则不发起新调用。已经在途的调用能否取消、是否收费取决于供应商，因此预算可能有明确界限内的结算偏差。

### 14.5 预算界面

始终显示已花费、预留、剩余额度和按阶段拆分。额度不足时用户可增加额度、缩小范围、导出当前成果或等待日额度恢复。系统不能自动购买套餐或把失败循环隐藏在“优化中”。

## 15 安全与数据控制

### 15.1 输入信任模型

用户在工作台明确提出的目标和授权属于指令；附件、架构图、仓库文件、网页、issue、代码注释、工具日志和模型输出都属于待分析资料。资料中的“忽略规则”“上传密钥”“执行此命令”等内容，不能提升为用户授权。规范文件可以提供工程偏好，但不能突破现有权限。

本次架构图用于理解系统设计，不作为执行任何程序、访问外部服务或修改用户环境的授权。产品同样需要在数据层记录内容来源，让提示构建器能区分用户请求与引用内容。

### 15.2 权限与凭据

密钥保存在操作系统凭据库或供应商正式支持的安全凭据设施，数据库只保存引用。工具进程获取最小必要权限和短期凭据，验证器不需要代码平台写权限。执行策略采用结构化工具和参数校验，避免将路径、文件内容或模型文本直接拼接到 shell。

文件检查解析真实路径、符号链接和挂载边界。网络默认限制为模型端点、已批准依赖源和必要开发服务；发现新的外部目标时说明用途。敏感动作按目标和参数授权，不能只用一份命令名称白名单保证安全。

### 15.3 数据流与删除

默认保留仓库、知识和运行日志在本机；使用云模型时，按需发送代码片段、任务和工具结果。界面提供“本次发送了什么”的分类视图与供应商链接。项目可禁用外部检索、关闭诊断上报，设置日志保留天数，并导出或删除本地数据。

本地删除包括数据库记录、产物、索引和缓存；已推送 Git、已创建 PR、已发送模型的数据分别受对应平台的规则控制。产品不承诺通过本机删除撤销这些外部副本，也不在没有合同依据时声称所有供应商不训练、不留存或满足特定法规。

### 15.4 桌面应用防护

关闭渲染层任意 Node 权限，使用受限 IPC、内容安全策略和经过校验的外链打开。执行不可信预览时隔离浏览器上下文，禁止预览内容访问本机控制 API。依赖和应用升级使用签名验证与版本回退；诊断报告在发送前展示脱敏摘要。

### 15.5 首版威胁测试

至少覆盖恶意 README 指令、issue 内嵌命令、日志伪造、符号链接越界、路径穿越、依赖脚本读取凭据、预览网页调用控制 API、生成代码伪造测试报告、取消后继续执行和跨任务文件污染。安全目标是明确边界内的防护效果，不宣称仅靠提示词即可完全防止注入。

## 16 非功能需求与运行维护

### 16.1 初始服务目标

以下为验收目标，尚未实测。个人工作台参考环境为 4 核 CPU、16 GB 内存、SSD；大型构建、测试和高并发执行允许使用独立 worker。规模验证按代码量、模块数、仓库数、依赖边数和历史任务数分层，覆盖十万行、百万行及更高规模。它们是待验证规模档位，不是已实现的性能承诺。模型、索引、执行和首次依赖下载时间分别统计。

| 维度 | 初始目标 | 测量方法 |
| --- | --- | --- |
| 本地反馈 | 命令提交到界面确认 P95 小于 500 毫秒 | 本地事件时间戳，不含模型响应 |
| 项目接入 | 标准示例仓库首次可运行任务小于 15 分钟 | 新设备安装流程录屏与事件 |
| 本地内存 | 工作台空闲常驻目标低于 600 MB | 排除浏览器验证、容器和模型服务 |
| 恢复 | 异常退出重启后 60 秒内给出可解释状态 | 故障注入，检查未知动作清单 |
| 数据完整性 | 已确认事务不丢失，未确认动作可核对 | 写入中断、进程终止、磁盘满测试 |
| 并发 | 由用户配额、依赖和 worker 能力共同限制，支持安全退回串行 | 任务、租约、冲突与进程配额测试 |
| 事件连续性 | 断线后能续传并去重 | 网络中断后比较事件序列 |
| 可访问性 | 键盘完成核心流程，状态有文本标签 | 键盘与对比度检查 |

对大型仓库采用分区索引、符号与接口摘要、增量更新和按需物化。用户交互不能等待全仓库扫描完成，索引就绪范围与缺口必须可见；索引与工作副本的版本不匹配时阻止错误引用。运行日志设置容量和保留策略，磁盘余量不足时停止新任务并允许导出和清理。

### 16.2 可观测性

记录任务、角色、步骤、工具、模型、用量、费用、失败类别和证据链接。用户界面展示行动摘要，开发诊断可以查看原始结构化事件。默认不上传原始提示词和源码；用户发送诊断时可逐项选择。

对每个版本建立适配器兼容矩阵，包括运行框架版本、操作系统、模型、认证方式、暂停与恢复能力。更新某个依赖后运行契约测试，不能只验证一个普通编码成功用例。

### 16.3 更新与备份

数据库升级先备份，迁移失败回到可读取旧版本的状态。备份使用 SQLite 正式备份流程或停止写入后的完整快照，不在运行中只复制主数据库文件而遗漏 WAL。凭据不混入普通项目备份；恢复到新机器时重新授权。工作区归档保留提交、差异和产物清单，删除前检查用户未提交内容。

## 17 指标与评估实验

### 17.1 核心指标

核心指标为“个人开发者接受并持续维护的项目里程碑”。里程碑必须有真实的跨模块集成基线、系统级验收和明确的未完成范围。局部任务数、生成代码行数和代理运行时长仅作为过程信息。

| 指标 | 定义与口径 |
| --- | --- |
| 里程碑验收率 | 通过系统级验收的里程碑 / 发起验收的里程碑 |
| 架构一致性 | 模块依赖、接口和约束检查的违规及修复情况 |
| 跨模块集成成功率 | 在完整版本集合上通过契约与关键路径检查的变更比例 |
| 变更影响遗漏率 | 集成或后续运行中发现未被影响分析覆盖的关联问题 |
| 个人协调负担 | 用户重复解释、重新定位和手工同步信息的时间 |
| 长期恢复质量 | 中断恢复后目标、约束、事实与未完成事项的保留情况 |
| 上下文效率 | 相同任务读取与传输的有效证据、重复上下文与费用 |
| 可持续维护性 | 后续变更是否仍可定位、验证和安全集成 |
| 运行费用 | 按任务、模块、里程碑和项目汇总真实费用与预留 |

按项目规模与变更复杂度分组统计，避免用大量简单任务掩盖跨模块工程问题。

### 17.2 离线任务集

局部能力测试建立至少 40 个可回放任务：10 个小功能、10 个缺陷修复、8 个维护、6 个跨模块改动和6 个环境或失败恢复任务。任务来自可授权的真实或自建仓库，固定起点、依赖和预期行为。另建至少 20 个恶意输入与权限边界案例，独立于普通任务成功率。

整体工程测试另设复合场景：跨子系统异步任务、公共接口兼容迁移、多仓库版本集成、长期中断恢复和后续维护。每个场景覆盖多项依赖任务及真实系统级验收，不能用局部任务集代替。

局部任务包括搜索、表单校验、分页、空状态、错误处理、权限检查、依赖升级和测试修复。每个任务由人工核验验收正确性，避免把模型生成的测试答案当作唯一真值。高波动配置重复运行三次，报告中位数、范围和失败分布，不用一次成功截图替代稳定性结论。

### 17.3 必做对照实验

E1 比较现有编码运行框架单独使用与 KFPA 完整闭环，观察人工修正时间、接受率和总成本。E2 在同一模型与基线上比较有无批准知识，观察有效帮助和错误引用。E3 比较相邻互审与独立验证的缺陷检出及误报。E4 比较固定强模型与任务路由，质量相近时再看成本。E5 比较串行和双任务编码，统计端到端时间、冲突和额外 CI 消耗。

固定任务、基线、模型与运行框架版本，实验一次只改变待验证因素。公开供应商案例只用来形成假设，不作为本产品的节省幅度承诺 [S01][S07]。

### 17.4 个人开发者的整体项目验证

邀请独立开发者在真实大型项目上完成跨模块功能、兼容迁移和长期维护三类任务。保留用户原有工作流作为对照，记录系统级结果、人工决策量、影响分析遗漏、集成返工和费用。

发布判定同时覆盖功能闭环、架构约束、权限边界、恢复和大规模索引。简单任务可用只是必要条件，只有在项目级验证中证明个人能持续掌握并推进全局，才符合产品核心目标。

## 18 超大规模软件的工程组织

### 18.1 分层工程地图

项目以总体目标、里程碑、子系统、模块和功能五层组织。工程地图记录每层的职责、依赖、接口、实现位置、当前基线、验收和未完成项。地图由实际代码与配置持续校验，模型推断的边必须标为待确认。

用户既能看到整体可运行程度，也能下钻到任务证据。局部完成率不能简单平均为项目完成率；一个关键依赖未完成，相关里程碑就不能宣称完成。

### 18.2 全局架构与局部上下文

全局规划器保留总体目标、领域边界、架构约束和关键决策，局部角色只获取负责模块的代码、接口及必要的相邻证据。跨层上下文通过版本化契约和引用连接，而不是向每个角色复制整个仓库。

架构规则包括允许的依赖方向、模块公共入口、错误与日志约定、数据所有权和兼容政策。规则变更先分析受影响子系统，再由用户确认；局部任务不能为了快速通过测试擅自改变全局约束。

### 18.3 接口先行与受控并行

跨模块功能先定义生产方、消费方、数据结构、错误语义和兼容范围，再分配实现任务。接口已冻结且无资源冲突的模块可以并行，依赖未确认时只允许设计或使用显式版本的测试替身。

全局配置、公共类型、依赖锁文件、数据迁移和共享资源设为受控变更区域。每个区域有逻辑写入所有权，锁冲突时排队或重新拆分。不能用不同文件目录代替语义依赖检查。

### 18.4 跨仓库集成基线

一个集成基线由各仓库完整提交、接口版本、依赖锁定、环境指纹和验证记录组成。变更集合明确必须一起生效的模块；版本控制平台不能原子合并多个仓库时，采用兼容性过渡、受保护集成分支和明确发布顺序。

常见迁移采用扩展、迁移、收缩：先加入兼容接口，再分批迁移调用方并验证，最后移除旧接口。任一步失败都能停留在可运行版本集合，不能依赖所有仓库同时切换成功。

### 18.5 长周期任务与维护队列

项目账本持续保存已确认目标、决策、依赖阻塞、已验证成果、待合并修改和技术债。新会话先恢复账本与真实仓库基线，再安排下一批任务。模型摘要是入口，原始证据和权威状态保持可回读。

缺陷、依赖升级、架构漂移和性能回归进入同一维护队列，并关联影响范围。系统定期提出可审查的维护建议，自动执行仍遵守用户授权和资源限制。目标是软件规模增长后仍能持续修改。

## 19 超大项目的验证与完成标准

### 19.1 分层验证

模块级验证检查实现和局部行为；接口级验证检查生产方与消费方契约；子系统级验证检查依赖协作；系统级验证覆盖核心用户路径、启动、升级和关键故障恢复。每层证据都绑定对应基线与环境，不能以模块测试总数替代系统验收。

### 19.2 规模验证矩阵

| 维度 | 验证场景 | 接受条件 |
| --- | --- | --- |
| 代码与索引 | 十万行、百万行和更高规模的可授权代码集 | 可增量检索，索引缺口与版本可见，前台操作不被全量扫描阻塞 |
| 模块依赖 | 大量模块、长依赖链、共享契约和循环候选 | 依赖可解释，循环可定位，变更影响可追踪 |
| 多仓库集成 | 多仓库提交组合与接口分批迁移 | 候选版本集合可重建，兼容阶段可运行 |
| 长周期执行 | 多次重启、跨会话、worker 断连和人工修改 | 无目标或约束丢失，无未知副作用盲目重做 |
| 并行执行 | 同时修改相关模块、配置和公共接口 | 所有权生效，无越权覆盖，集成证据有效 |
| 系统维护 | 后续功能、缺陷修复、依赖更新和撤销 | 原成果可继续理解、修改、验证和维护 |

具体性能数据应连同硬件、项目形态、索引方式和执行资源公布。规模档位用于检验能力，不承诺任意代码库在固定设备上达到相同速度。

### 19.3 里程碑完成定义

里程碑完成需要范围内模块形成一致版本集合、关键接口契约通过、系统级验收通过、阻塞问题处理完毕，并保留运行和恢复说明。用户可接受明确的非阻塞技术债，但系统不能隐藏它们或把未验证内容标为通过。

### 19.4 发布阻断条件

用户工作区可能被覆盖、权限无法限制、费用无法解释、重启可能重复外部操作、证据不绑定候选版本、跨模块契约不一致、集成基线不可重建，均阻止相关成果自动集成或发布。更多模型调用和更多局部测试不能替代这些条件。

## 20 完整功能示例

### 20.1 项目目标

个人开发者构建一个支持扩展插件的大型开发平台。系统包含身份权限、项目工作区、文件与索引、后台任务、插件运行时、Web 界面和可观测性等子系统。这里用“插件异步任务”展示一个跨模块垂直切片；完成此切片不代表整个平台完成。

### 20.2 功能与契约

需求是插件可提交异步任务，用户能在项目界面查看状态和结果，取消后任务不能继续写入。架构约束包括插件不能直接访问调度数据库、任务必须绑定项目权限、结果必须属于明确版本和工作区。

先定义提交、状态查询、取消与结果接口；确认任务标识、租约、权限、重试、错误和结果所有权。接口变化关联插件运行时、权限服务、任务调度、产物存储和前端消费方。

### 20.3 任务图与局部执行

全局规划器维护该切片的依赖图和里程碑验收，模块角色分别实现权限、调度、结果存储和界面。接口冻结后，调度实现与前端测试替身可以并行；真实端到端验证必须等待相关模块形成兼容版本集合。

所有任务使用独立工作区，公共契约只由获授权任务修改。局部角色发现接口缺陷时提交变更请求，由协调器分析全部消费方，而不是在本模块自行补一个不兼容字段。

### 20.4 分层验收与集成

模块测试验证局部实现；契约测试验证生产方和消费方；系统验收验证用户提交、查看、取消和读取结果的完整路径。故障案例包括 worker 失联、重复提交、取消竞态、权限撤回和部分仓库升级失败。

协调器生成包含各仓库提交、契约和环境版本的集成基线。只有实际组合验证通过后，用户才能接受该里程碑成果。部分模块仍失败时，界面保留已完成结果并展示阻塞链，不能将局部通过呈现为系统完成。

### 20.5 长期演进

下一阶段增加新插件能力时，系统检索已批准的接口决策和故障案例，分析已有调用方，在兼容阶段分批升级。跨会话保存整体目标与技术债，使个人开发者可以持续推进整个平台，而无需每次重新理解全部代码。

## 21 风险与待验证决策

| 风险或假设 | 早期信号 | 应对与决策负责人 |
| --- | --- | --- |
| 全局掌握能力不足 | 用户仍需反复手工同步模块和接口 | 验证工程地图、影响分析与关键决定呈现 |
| 多角色总成本过高 | 验证与规划成本超过实现且帮助有限 | 执行负责人按任务类别减少角色和上下文 |
| 可选环境配置失败 | Docker 镜像、SSH 登录或远端工具链不可用 | 提供分后端诊断，不阻塞其他项目，不自动切换执行环境 |
| 模型和测试共同误解需求 | 验收绿色但用户拒绝 | 质量负责人改善契约、反例和人工判断项 |
| 组件和知识过期 | 引用后导致重复环境错误 | 知识负责人增加版本和失效触发 |
| 并行增加集成时间 | 编码变快但合并和 CI 变慢 | 默认保持串行，以实测决定开放范围 |
| 供应商接口或授权变化 | 恢复、事件、费用能力失效 | 适配负责人固定版本、能力探测与回退 |
| 预算硬限制不可靠 | 未结算调用超出预留 | 费用负责人收紧最大调用量或降级承诺 |
| 本地数据泄露 | 日志、预览或插件暴露源码和密钥 | 安全负责人收缩权限、隔离预览与审核导出 |
| 局部完成掩盖整体不可用 | 大量任务通过但关键路径无法运行 | 用集成基线和里程碑验收约束完成状态 |

### 21.1 试用前需要确定

需要通过工程验证确定索引规模边界、模块与仓库映射、接口版本机制、DeepSeek 默认角色档位映射、自定义模型配置、正式执行适配器、worker 租约与恢复、系统级检查配置和预算执行能力。

默认采用个人控制入口、分层项目模型、自带密钥、隔离工作区、按依赖推进、用户审查关键设计和可重建集成基线。执行资源可以从单机起步，但架构不能将项目永久限制在单仓库或单会话。

### 21.2 最终推荐

围绕“个人能够完成超大软件开发与维护”组织产品。总体目标和架构建立全局方向，模块与接口承接拆分，功能任务推进局部实现，集成基线与系统验收证明整体成果，长期记忆支持持续演进。

产品需要同时让执行规模可以增长、个人的决策负担保持可管理。功能流水线是执行机制，完整项目的可运行性、可理解性和可维护性才是最终结果。
