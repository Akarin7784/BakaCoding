## 3. 整体架构

```
旗舰评审组（多模型，必填主管 max）
   │ 拆工程 → 写入范围互不重叠的需求单                      ▲ 超过复投上限的单退回重拆（假设 A8）
   ▼                                                         │
每张需求单 → 一个副 Agent（随需求单水平扩展）
   ├─ 写编码提示词 → 临时 Flash 代理（受限工具，写完即销毁）→ 补丁
   ├─ 在自己的 PR 上跑一次快速 CI（编译/lint/受影响单测）+ 一次评审
   └─ 没过 → 原地复投给新的 Flash 代理重写（上限，假设 A8）
                 │ 通过
                 ▼
         单一合并队列：按批跑一次完整 CI，通过整批合并，失败二分定位
         （按依赖顺序；冲突在新基线上重投，假设 A6；CI 积压超限 → 编码池降并发 / 暂停派单）
```

## 4. Flash 编码池设计

设计方向和待定参数，不含性能数字。相关事实见 `bakacoding-flash-concurrency-research.md`。

### 4.1 单张需求单的生命周期（已定 + 假设）
1. 副 Agent 领取需求单（需求单已声明写入范围和依赖）。
2. 副 Agent 写编码提示词，系统为该单创建独立 worktree，启动一个临时 Flash 代理。
3. Flash 代理在受限工具下完成编码，产出补丁后销毁（已定）。
4. 副 Agent 通过系统提交、开 PR，在本地跑**一次快速 CI**（编译、lint、受影响单测）、做**一次评审**（已定）。
5. 任一不过：副 Agent 带上失败信息原地复投，新开 Flash 代理重写（已定）；复投上限建议 3 次，超限上报主管重拆（**假设 A8**）。
6. 通过：进入单一合并队列，按批跑完整 CI（已定，见 4.11）；批失败时二分定位出问题 PR，退回第 5 步复投。

### 4.2 Flash 代理工具白名单（项目负责人 已定「严格限制」；具体项为建议，待确认 D16）
| 允许（建议） | 范围 |
|---|---|
| 读文件 | 仅限自己的 worktree |
| 写 / 编辑文件 | 仅限需求单声明的写入范围；越界写入由系统拒绝 |
| 列目录、搜索代码 | 仅限自己的 worktree |

| 不给（建议） | 由谁做 |
|---|---|
| shell / 任意命令执行（含构建、测试） | 快速 CI 由副 Agent 通过系统运行；完整 CI 由合并队列运行 |
| 网络访问 | — |
| git 提交、推送、开 PR | 副 Agent / 系统 |
| 包安装、改依赖清单 | 05:19 已定：依赖类需求单由 Flash 只改清单文件，评审时标为高风险；实际安装由用户自己的 CI 负责，v1 不管 |

说明：路径校验要解析真实路径、处理符号链接（沿用 `product-design.md` §8.2 的要求）。不给 shell 意味着 Flash 不能自测，所有验证集中在副 Agent 的那一次 CI 上；是否给只读的测试运行工具，列入 D16。

### 4.3 并发数
- 池并发 N = 同时在跑的需求单数 = 同时存在的副 Agent 数（副 Agent 随单水平扩展）。
- 上限来自：CI 吞吐（快速 CI 与批量完整 CI，见 4.11，常是最先到顶的一项）、服务商限额（DeepSeek 按账号并发，千问按主账号 RPM / TPM，多 key 不增加额度，见 `01` 第 1–2 节）、本机资源（worktree、CI 进程）、预算、合并队列吞吐。估算公式见 `01` 第 5.5 节，本计划在其中加入 CI 项：

```
N_ci_fast = c_fast × T_code / T_fast           # c_fast：快速 CI 可并发数；T_fast：单个 PR 快速 CI 平均时长
N_ci_full = (c_full × b / T_full) × T_code     # c_full：完整 CI runner 数；b：平均批大小；T_full：单批完整 CI 时长
            × (1 − f)                          # f：批失败触发二分重跑带来的额外开销比例（实测）
N_ci      = min(N_ci_fast, N_ci_full)
N         = floor( min(N_api, N_local, N_budget, N_review, N_ci) × s )
```

所有参数运行时实测后再填；运行中由反压（4.11）动态下调 N。默认上限 8、硬上限 64（初始值，待实测）（D7，05:37）。

### 4.4 任务切分粒度
- 一单 = 一个 Flash 代理 = 一个 PR：一次连贯、小范围的改动，声明写入范围、依赖接口版本。
- 跨模块大改由主管拆成「接口先行 + 若干独立实现单」；依赖清单、锁文件、全局配置、迁移、公共类型属于独占区域，单独排队。

### 4.5 调度与队列
- 就绪条件：依赖已合并或接口已冻结；写入范围与在途单不重叠（**假设 A9**：并发单写入范围不重叠，调度器按逻辑锁保证）。
- 两个队列：就绪队列（待开副 Agent）和合并队列（待批量完整 CI / 待合并 PR）。CI 积压超上限时就绪队列降速或暂停（反压，见 4.11）。
- 单一协调器写状态：排队 → 编码中 → 快速 CI / 评审中 → 复投中 → 合并队列（待批）→ 批量完整 CI → 已合并 / 二分定位后退回复投 / 退回重拆。

### 4.6 worktree / 文件隔离与并发冲突
- 每单一个 worktree + 分支，从同一确认基线创建；Flash 代理销毁后 worktree 保留到 PR 合并或放弃再清理。
- 事前：写入范围不重叠（A9）。事后：合并队列按依赖顺序组批，在最新主干上跑批量完整 CI；冲突时在新基线上重投给 Flash（**假设 A6**）。
- worktree 不隔离语义冲突、端口、数据库、缓存（`01` 第 4 节）；接口依赖由评审组在需求单里显式声明。

### 4.7 限流与重试
- 协调器统一令牌桶限流，所有 Flash 代理共享；429 指数退避加抖动；启动时逐步放量（千问有突发激增保护，见 `01` 1.2）。
- 网络 / 限流重试与「CI / 评审不过的复投」分开计数；复投有上限（A8），网络重试另设上限。

### 4.8 失败回退
- 复投超限 → 上报主管重拆（A8）。
- 复投升档（D10，05:37，取代旧的「默认不自动切换」）：默认开启自动升档，第 1 次复投仍用 `low`，第 2、3 次用 `high`；不自动换模型，换模型由主管决定。
- 服务商不可用时任务暂停排队，不静默换服务商。

### 4.9 成本
- 主要由并发数、单单输入上下文、复投次数决定。临时代理每次冷启动都要重读上下文，所以提示词要「稳定公共前缀在前、需求单在后」以提高前缀缓存命中（DeepSeek 缓存按前缀完全匹配，与代理是否销毁无关，见 `01` 1.1、5.1）。
- 可把批量编码排到 DeepSeek 闲时（闲时价为高峰价一半，见 `01` 1.1）。
- 费用台账按需求单（含复投）、副 Agent、评审组分列。

### 4.10 低思考档位
- **已定**：Flash 编码代理默认思考档位 `low`，用户可按项目 / 单次运行配置（沿用配置优先级：单次运行 > 项目 > 用户 > 内置默认）；每次调用记录实际档位。复投自动升档默认开启：第 1 次复投仍 `low`，第 2、3 次 `high`；不自动换模型（D10，05:37）。注意：官方没有公开 `low` 档的编码 benchmark；非思考模式比 High 在 SWE-bench Verified 上低约 5 个百分点、在 LiveCodeBench 上差距更大（V4-Flash 官方数据，见 `01` 第 3 节）。这支持「需求单尽量清楚、局部」的拆单原则。
- 不支持的档位报错，不静默改档；默认模型按 E3 保持 DeepSeek V4.1-Flash（D8）。

### 4.11 评审、合并队列与反压（v1，2026-10-17 05:14 改写；原 CI 分层方案作废，

- **CI 不在 v1 范围**：由用户自行配置 CI 和远程 git。BakaCoding 不跑编译、lint、测试，也不管 runner。
- **单张需求单的把关**：副 Agent 推到工作分支后直接开 PR，然后做一次评审。评审对照需求单看 diff：是否完成需求、是否越出需求单范围、有没有明显 bug、是否违反架构约束。用户仓库配了 CI 时，可以读取 GitHub check 结果（可选），失败算不通过。不通过就原地复投，把评审意见带回给 Flash；上限 3 次，超了上报主管。
- **合并队列**：排队，按依赖顺序合并，合并前检测冲突；有冲突就基于最新集成分支原地复投。不按批跑完整 CI，也不做二分定位（原 C2、D21 作废）。默认合入集成分支，自动合入主干是 L2 开关（C5）。
- **反压**：按评审吞吐（在途待评审的 PR 数）和 API 并发 / 限额动态调整编码并发；积压超过上限就降并发或暂停派单，恢复时逐步放量。阈值见 §5.5（D20，05:37）。

## 5. 整体设计（按模块；2026-10-17 05:17 定稿结构，以本节为准）

> 现阶段只做整体设计，不划分开发切片（项目负责人 05:17）。§3–§4 中与本节冲突的旧内容以本节为准；05:35 设计评审的 6 条修订已并入本节。CI 不在 v1 范围内，v1 不执行代码（见顶部范围变更框）。决策来源见 `bakacoding-design-backlog.md` 的决策记录。

### 5.0 需求单（E5，05:23）
- 需求单仿照派子任务时的自然语言消息，写清：目标、背景与上下文、改动范围、完成标准、回报内容；另含接口声明和上下文包（05:21）。不用 YAML 字段表。
- 两类复投计数是运行时状态，记在 PR 记录里，不写进需求单（05:21）。
- 「完成标准」只是需求单里的一项内容，不代表另做验收设计。

### 5.1 Flash 编码池
- 每张需求单开一个临时 Flash 代理，写完即销毁。默认思考档 `low`，用户可配（已定决策 1、6）。
- 并发 N 只计编码阶段的单；PR 等待合并时不占编码槽位（C3，05:08）。
- 协调器统一用令牌桶限流（由模型接入适配层实现，见 5.7），429 时指数退避加抖动，平滑放量（§4.7）。
- 每单一个 worktree，从确认基线创建；依赖已合并才放行（C1，05:08）。
- 导入项目时按清单文件识别语言，结果只作为评审和切单的上下文；没有镜像，也没有测试命令（D-E1，05:14）。
- 开发自测用一个开源 Python 仓库，只当真实代码，不跑测试，用来测复投率、评审质量、冲突率（05:16）。
- 模型：DeepSeek V4.1-Flash（E3，05:23）；开发阶段所有角色都用 DeepSeek Flash，靠档位、角色提示词和权限区分（开发配置，不是产品设计，05:40，见 5.6）；「是否只用国产模型」已划掉。技术栈：Node/TS + Electron + SQLite（E2，05:23）。
- D7（05:37）：N 按 `01` 第 5.5 节公式计算，默认上限 8，硬上限 64（初始值，待实测）；超过硬上限须用户手动改配置。
- D10（05:37）：默认开启自动升档，第 1 次复投仍 `low`，第 2、3 次 `high`；不自动换模型，换模型由主管决定。

### 5.2 受限工具层（E4 定稿，05:25）
- **Flash 的权限由副 Agent 按单现场设计**，不由系统写死。副 Agent 读完需求单后决定：给哪些工具，可读写哪些文件，能否新建、删除、重命名。
- **写权限必须落在本单写入范围以内**（05:35）。Flash 中途需要更多权限时向副 Agent 申请，副 Agent 当场批准或拒绝；申请的写权限超出本单写入范围时，副 Agent 不能直接批，要交给调度器重新加锁，加锁失败就上报主管（05:35）。
- **系统外层硬边界**（副 Agent 也不能越过）：只能在本单工作区内；不给 shell、网络、git；密钥和 `.env` 类文件不放行。路径按真实路径解析，处理符号链接（§4.2）。
- 副 Agent 给出的权限清单（含中途的批准和拒绝）写入 PR 记录，评审时一并审查。
- v1 的 Flash 和副 Agent 都不执行代码，没有测试工具（05:16）。外发前脱敏，worktree 不带入未跟踪的密钥（02 G1）。
- 依赖类需求单：Flash 只改清单文件，不装包；评审时标为高风险；实际安装由用户自己的 CI 负责（05:19）。
- 本节取代此前的固定读 / 写 / 列 / 搜白名单（D16 05:16 版）和 05:19、05:23 的各版建议。

### 5.3 副 Agent 与 PR 抽象
- 一单一个副 Agent，负责写提示词、设计 Flash 权限、开 PR、发起评审和复投，随需求单水平扩展（已定决策 4）。模型可配置（`sub_agent`）；正式版默认旗舰模型，开发阶段用 DeepSeek Flash `high`（05:35 定、05:40 修订）。
- **PR 抽象**（05:16）：一套接口两种实现。
  - 有 GitHub：推到工作分支后直接开真 PR（C4，05:14）。
  - 没有远程仓库：建本地工作分支，加一条 PR 记录（diff、需求单、评审结论、副 Agent 给出的权限清单、两类复投计数），合并就是本地合进集成分支。
- **本地记录为准**（05:17）：
  - 状态、复投次数、评审结论都以 BakaCoding 自己的记录为准；GitHub PR 只是同步出去的展示和合并通道。
  - 两边不一致时以本地为准，差异记进日志。
  - 用户在 GitHub 上手动关闭或合并 PR 时，同步回本地，交给主管 Agent 处理（E7，05:23）。
- GitHub 合并由 BakaCoding 主动发起：合并队列轮到、冲突检测通过后，把 PR 合入集成分支（05:21）。

### 5.4 评审与复投
- 每张单的唯一质量闸门是一次单评审：对照需求单审 diff，看是否完成需求、是否越出需求单范围、有没有明显 bug、是否违反架构约束（05:14）。
- 用户仓库配了 CI 时，可选读取 GitHub check 结果，失败算不通过；我们不跑 CI（05:14）。
- **评审模型按负载分配**（05:17）：
  - 评审组里除主管外的旗舰模型组成评审池，每张单分给当前空闲的模型。
  - 同一张单复投后仍由原来的模型评审。
  - 被限流的模型自动跳过。
  - 这条取代 05:16 的「默认用其中一个旗舰模型」。
- 不通过就原地复投，把评审意见带回给 Flash；回灌内容截断，并标注为不可信（02 G2）。
- 复投上限分开计数：评审不过 ≤3 次，合并冲突 ≤2 次，任一超限就上报主管重拆（C6，05:16）。同一需求重拆 2 次仍不通过，就停下来交给用户（`pipeline.resplit_limit`，05:35）。
- 基线前进后，如果本单涉及的接口或依赖有变化，重新评审一次，不计入复投次数（05:35）。
- 记录复投率和评审不过的原因（05:16）。
- 依赖类需求单（改清单文件）在评审时单独标为高风险（05:19）。原独立验证器（D14）已正式删除，职责并入本评审（05:19）。
- 风险 R1：高，见 §7。

### 5.5 合并队列与反压
- 合并队列只做三件事：排队、按依赖顺序合并、合并前检测冲突（05:14）。
- 有冲突就基于最新集成分支原地复投；副 Agent 不解冲突（D9 v2 再议，05:16）。
- 不按批跑完整 CI，也不做二分定位（C2、D21 作废）。
- 写入范围逻辑锁与独占区域（A9、§4.4）；副 Agent 授予的写权限受该锁约束（5.2，05:35）；接口按生产者→消费者排序（02 G6）。
- **合入 main 前的检查**（05:35，两种模式都必须先完成）：主管审一遍集成分支的整体 diff；用户仓库配了 CI 的，必须读到集成分支为绿才能合。理由：写入范围不重叠挡不住语义冲突，v1 又不执行代码。
- 默认合入集成分支。合入 main 由配置 `pipeline.main_merge`（草案名）决定：`user`（默认，集成分支攒够并通过上述检查后主管通知用户自行合入）或 `supervisor`（检查通过后主管直接合入 main，合完通知用户）（项目负责人 05:26、设计负责人 05:26；修订 C5）。
- 评审池全忙或全部限流时，单子排队等待，不交主管；评审池满即触发反压、暂停派新单（05:21）。
- 反压：按评审积压和 API 并发降并发、暂停派单、逐步恢复，并记录原因。主管待办队列也计入反压，积压超过 `pipeline.supervisor_backlog_limit` 时暂停派新单（05:35）。成本触顶也降并发（E6，05:23）。
- 反压阈值（D20，05:37，均为初始值，待实测）：评审容量 = 评审池成员数 × 每成员并发评审数（默认 2）；成员数为 0 时按 1 个成员计，即容量为 2（05:40 已定）。评审积压超过容量 2 倍，编码并发减半；超过 4 倍，暂停派新单；积压回落到容量以下后，每 5 分钟加 1 个编码槽位，直到回到 N。`supervisor_backlog_limit` 默认 10。
