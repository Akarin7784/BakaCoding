# BakaCoding 计划整体评审（独立架构师视角）

> 评审对象：`bakacoding-analysis-and-design.md`（2026-10-17 05:04 版，含 CI 与反压一节）。对照：`bakacoding-flash-concurrency-research.md`，以及仓库 本仓库（HEAD `a106ddc`，纯文档）。
> 只评审，不改计划文档。不写验收设计，不写数字。
> 严重度：**阻断**（不解决就无法开工或会出事故）/ **严重**（会导致返工或方案失效）/ **一般** / **建议**。

## 0. 最重要的结论

1. **安全边界空缺（阻断）**：Flash 能读整个 worktree，worktree 里可能有 `.env` 和密钥，读到的内容会发给云模型。仓库文件里的提示注入没有防护。模型生成的代码会在副 Agent 本地和自托管 runner 上直接执行，而计划对执行隔离只字未提。
2. **首个目标语言 / 样例工程未定（阻断）**：CI 分层、受影响单测、增量构建、工具层全部依赖具体语言工具链。仓库 §4.1 也要求「一种语言 + 一种适配器」先跑通，计划里没有对应的决策项。
3. **持久化、崩溃恢复、预算硬上限被放到 M5（严重）**：从 M1 开始就是 N 路并发、自动复投、批量 CI，这几样不在 M1 就位，成本和状态都会失控。
4. **需求单质量是全链路风险最高的假设，却最后才做（严重）**：低档位、无 shell、冷启动的 Flash 能否写好代码，几乎完全取决于需求单和上下文质量。M1–M3 用手写单，M4 才有评审组拆单，要到最后才知道核心假设是否成立。
5. **流程语义有几处自相矛盾（严重）**：
   - 「接口已冻结但未合并」就放行依赖单，依赖单的快速 CI 编译不过。
   - 「按依赖顺序组批」与「二分定位」冲突：拆半会把依赖对拆开。
   - 副 Agent 的生命周期没定义：等合并期间它算不算并发 N？
   - 「本地快速 CI，不占正式 CI」和「先开 PR」冲突：开 PR 通常会自动触发正式 CI。
6. **自动合并与用户控制冲突（严重）**：普通 PR 通过后直接进合并队列合入，而仓库 §4.3 规定首版默认 L1、L2 自动集成需用户开启，计划的 A3 也说用户可否决，两者没有对齐。

## 1. 内部矛盾与前后不一致

| # | 问题 | 位置 | 严重度 | 修改建议 |
|---|---|---|---|---|
| C1 | 就绪条件允许「接口已冻结（未合并）」，但每单 worktree 从确认基线创建，依赖单拿不到未合并的接口代码，快速 CI 必然失败，被白白复投 | 4.5、4.6 | 严重 | 就绪条件改为「依赖已合并」；如果要提前开工，需求单要携带接口桩，或基线改为「主干 + 依赖 PR」的集成分支，二选一写进 ADR |
| C2 | 合并队列「按依赖顺序组批」+「失败二分定位」：二分把批拆两半时，若依赖方和被依赖方分到两边，那一半必然失败，定位结论错误 | 4.11-2、4.6 | 严重 | 规定依赖链上的 PR 不同批（或整链作为一个不可拆单元）；二分以「依赖闭包」为单位拆 |
| C3 | 「池并发 N = 同时存在的副 Agent 数」，但副 Agent 在 PR 进入合并队列后是否存活没有定义。存活则 N 被等待合并的单占满、编码池空转；销毁则批失败后由谁复投没有着落 | 4.3、4.1 第 6 步 | 严重 | 把「编码槽位」和「PR 所有者」分开：N 只计编码 + 快速 CI 阶段；副 Agent 交出 PR 后释放槽位，状态写入协调器，批失败时由新副 Agent 按记录接手 |
| C4 | 「副 Agent 本地跑快速 CI，不占正式 CI」与「系统开 PR」：如果仓库的 GitHub Actions 配置了 `pull_request` 触发，每次开 PR 和每次复投 push 都会触发正式 CI，等于没分层 | 3、4.1 第 4 步、4.11-1 | 严重 | 改为「快速 CI 通过后才推送 / 开 PR」，或正式 CI 只用 `merge_group` 触发（GitHub 文档说明 merge queue 需要 `merge_group` 事件，见 `01` 第 4 节链接）；写清每次复投是否新开 PR |
| C5 | 自动合入主干与仓库 §4.3「首版默认 L1，L2 受控集成需用户开启」、计划 A3「用户可否决合并结果」不一致 | 3.1 A2/A3、4.11 | 严重 | 增加显式的用户介入点：默认合入集成分支，用户确认后再进主干；或把「自动合入主干」作为 L2 开关，默认关 |
| C6 | 已定决策写的是「一次 CI + 一次评审，没过就复投」，但又引入了批量完整 CI 失败后的二次复投；复投上限 A8 是否把批失败也算进去没说 | 已定 4/7、4.1、A8 | 一般 | 复投计数分两类（快速 CI / 评审失败、批量 CI 失败），分别定上限，或明确合并计数 |
| C7 | 白名单「写 / 编辑仅限写入范围」，但新建文件、删除文件、重命名是否允许没写；包安装和改依赖清单「需单独需求单」，可 Flash 本身不能装包，那张单由谁执行也没写 | 4.2 | 一般 | 白名单补「新建 / 删除 / 重命名（限写入范围）」；依赖变更单由系统执行安装、Flash 只改清单，或由副 Agent 执行 |
| C8 | 公式里还保留 N_review（沿用 `01` 5.5），但新流水线中评审已经随副 Agent 水平扩展，不再是独立池；真正的瓶颈是评审所用模型的限额（与 Flash 同服务商时会和编码抢同一账号额度） | 4.3 | 一般 | 把 N_review 改写为「评审调用占用的 API 限额」，并计入 N_api；若评审与 Flash 同账号，两者共享 C_max / RPM |
| C9 | 第 1 节「设计里已定的关键技术取向」仍写「主 BOT max、次 BOT high」，而后文已取消主 BOT，读者容易误以为仍是现行设计 | 1 | 建议 | 加注「以下为仓库现状，已被第 3–4 节新架构取代」 |

## 2. 漏掉的关键环节

| # | 环节 | 现状 | 严重度 | 修改建议 |
|---|---|---|---|---|
| G1 | **密钥与数据外发** | Flash 可读整个 worktree（含 `.env`、配置里的凭据），读到的内容进入云模型请求；仓库 §15、FR17 有凭据要求，计划里没有 | 阻断 | 读工具加拒读清单（`.env*`、密钥文件、`.git` 内部）和内容扫描；worktree 创建时不带入未跟踪的密钥文件；外发前做脱敏检查 |
| G2 | **提示注入** | Flash 和副 Agent 都会读仓库文件、CI 日志、评审意见；仓库 §15.1 / FR03 要求「输入来源隔离」，计划没提 | 严重 | 白名单之外的任何「指令」不提升权限（工具层本身已限制，这是优点）；评审模型和副 Agent 的提示里显式标注不可信内容；CI 日志回灌给 Flash 前截断、过滤 |
| G3 | **执行隔离** | 快速 CI 在副 Agent「本地」直接执行模型生成的代码；完整 CI 计划用自托管 runner。计划里没有任何隔离说明。worktree 不隔离进程权限（仓库 §12.3 原文） | 阻断 | 快速 CI 默认放在容器或受限用户下跑（仓库已有可选 Docker 后端）；自托管 runner 只用于私有仓库，且每次任务后重建环境；GitHub 官方安全指南对公开仓库使用自托管 runner 有明确警示，选型时需核实 |
| G4 | **上下文供给** | Flash 只有读 / 列 / 搜索工具、低档位、每次冷启动，「它需要读什么」完全靠副 Agent 的提示词。仓库 §10（知识优先、知识卡片、上下文预算）是原设计核心，新计划中消失了 | 严重 | 需求单 schema 增加「上下文包」：必读文件、接口定义、相关约定、示例代码片段；由协调器预先组装成稳定前缀（同时利于缓存命中，见 `01` 1.1）；把仓库 §10 降级保留为 M2 / M4 的一部分 |
| G5 | **需求单质量闸门** | 需求单进入编码池前没有任何检查（写入范围是否合理、是否足够小、是否自洽） | 严重 | 增加「需求单校验」步骤：schema 校验 + 写入范围与依赖的静态检查 + 可选的评审组抽检；复投超限的单要统计回流，用来改进拆单 |
| G6 | **语义冲突** | 写入范围不重叠只防文本冲突；`01` 第 4 节引用的资料指出 worktree 挡不住语义冲突、约 42% 的冲突是结构性的。计划只靠批量完整 CI 兜底 | 严重 | 需求单声明「消费 / 产出的接口」，调度器对同一接口的生产者与消费者强制排序；公共类型列为独占区域（计划已有）之外，再加「接口变更单先合，消费方在新基线上开工」 |
| G7 | **持久化与崩溃恢复** | M1–M4 只提「单一协调器写状态」，没有持久化；断点恢复放在 M5。仓库 §12.4、FR09 已有单写入者 + 租约 + 恢复设计 | 严重 | 协调器状态存储（仓库建议 SQLite + WAL）和幂等键放进 M1；重启后要能识别在途的 Flash 调用、未推送的补丁、已开的 PR，不重复开 PR |
| G8 | **成本失控** | N 路并发 × 复投上限 × 批失败二分重跑 × 评审调用，全部自动进行；预算台账在 M5。`01` 1.1 记载 Artificial Analysis 评价 V4.1 Flash「very verbose」，输出 token 偏多 | 严重 | 预算预留与硬上限（仓库 §14.4）放进 M1；每单设输出上限；按单统计含复投的总花费，超阈值自动停派 |
| G9 | **可观测性** | 实时视图在 M5，M1–M4 没有日志、指标、追踪要求 | 严重 | M1 起就要有结构化事件日志（每次调用的模型、档位、token、缓存命中、耗时、结果），每单可追溯从需求单到合并的完整轨迹；反压决策本身也要记录原因 |
| G10 | **用户介入点** | 除了「可否决」（A3）之外，没有定义用户在哪些节点必须确认：需求单批量下发前、高风险 PR、主干合并、预算触顶、复投超限 | 严重 | 列出介入点清单和默认行为（暂停等待 / 继续），与仓库 §6.8「打断策略」对齐 |
| G11 | **Flaky 测试** | 批量 CI + 二分对偶发失败很敏感，一个 flaky 测试会让整批反复失败、触发无效复投；GitHub merge queue 有「只合并未失败 PR」的选项专门处理偶发失败（见 `01` 第 4 节文档） | 一般 | 二分前先重跑一次失败的检查；记录 flaky 名单并隔离；flaky 导致的失败不计入复投次数 |
| G12 | **GitHub API 与 PR 噪音** | 每单一个 PR、每次复投 push，大量调用 GitHub API；本次研究未查 GitHub API 限流 | 一般 | 补查 GitHub REST / GraphQL 限流文档；考虑复投期间不推送远端，只在快速 CI + 评审通过后推送并开 PR |
| G13 | **基线漂移** | 长时间排队的单基于旧基线；计划只在冲突时重投，没有「基线太旧就主动 rebase / 重派」的规则 | 一般 | 在就绪和入队两处检查基线落后程度，超过阈值先 rebase 再快速 CI |
| G14 | **评审本身的质量** | 副 Agent 的评审用什么模型、看什么（diff + 需求单 + 上下文包？）、输出格式、如何避免与 Flash 同模型同盲区，都没写（只有 D18） | 一般 | 评审输入输出做成 schema；评审标准与需求单字段一一对应；评审模型与 Flash 不同档或不同模型作为默认 |

## 3. 风险最高的假设

| # | 假设 | 为什么风险高 | 严重度 | 建议 |
|---|---|---|---|---|
| R1 | 低档位、无 shell、冷启动的 Flash 能在 3 次以内写出过关代码 | 官方没有 `low` 档的编码 benchmark；非思考模式相对 High 有明显降幅（`01` 第 3 节）；Flash 不能自测，只能靠「CI 失败信息 → 重写」盲改 | 严重 | 最早做一次小规模试跑（M1 内），用真实需求单观察复投率，再定 A8 和 D10；D16 认真考虑给 Flash 一个受限的「运行指定测试」工具 |
| R2 | 评审组能把工程拆成「写入范围不重叠、足够小、自洽」的需求单（A1、A9） | 这是编码池能否并发的前提，而计划 M4 才实现；拆不开时并发度会退化为串行 | 严重 | 把「拆单」提前：M1 之后先做最小拆单器（单模型即可），评审组的多模型协作放后面 |
| R3 | 「受影响单测」能可靠判定 | 依赖具体语言和项目结构；判不准就退回保守集，快速 CI 变慢，分层的意义变小 | 一般 | 首版直接用「模块级保守集」，测试选择作为后续优化，不放在 M2 关键路径 |
| R4 | 批量 CI + 二分能显著降低 CI 压力 | 收益取决于批失败率；失败率高时二分会多跑很多轮。没有本项目数据 | 一般 | 批大小做成可动态调整（失败率高就缩小批），先用小批 |
| R5 | 单账号限额不是瓶颈（`01` 结论） | 对 DeepSeek 并发上限成立，但评审组、副 Agent 评审、Flash 共用同一服务商时会共享额度；百炼有突发保护 | 一般 | 按角色分账号或分服务商，或在令牌桶里按角色配额 |
| R6 | 多旗舰评审组的成本可接受 | 每次设计、拆单、高风险评审都是多模型 × max 档 | 一般 | 评审组成员数和参与场景做成配置；非关键场景只用主管 |

## 6. 其他建议

- **（建议）术语统一**：「CI」现在同时指快速 CI 和完整 CI，「评审」同时指副 Agent 评审和评审组评审。文档里固定用「快速检查 / 合并检查」「单评审 / 组评审」，避免实现时理解偏差。
- **（建议）仓库现有设计的大量内容可以复用**：§8.2 任务包、§9.4 幂等键、§12.4 单写入者 + 租约、§14.4 预算预留、§15 安全，都与本次评审的漏项直接对应。改版时不要随角色调整一起删掉。
- **（建议）README 的对外承诺**：仓库 README 写的是「知识优先、架构约束、系统级验收」，新定位是「Flash 编码池」。改版时要说明两者的关系，避免对外叙事断裂。
